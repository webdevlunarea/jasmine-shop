## API contract currently present

Base path: `/api/v1`. Responses use `{success,data,meta}` or `{success:false,error}`.

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/auth/login` | Public, throttled | Verified customer login; returns short access and rotating refresh tokens |
| POST | `/auth/refresh` | Refresh token | Rotate refresh token; reuse revokes its token family |
| POST | `/auth/password-reset/request` | Public; CAPTCHA when enabled | Enumeration-safe OTP request using email/username and existing server-side limits |
| POST | `/auth/password-reset/complete` | Public; OTP proof | Complete password reset, rotate password-session version, and require login again |
| POST | `/auth/register` | Public; throttled; CAPTCHA when enabled | Create pending customer account, send email verification code, and grant no session |
| POST | `/auth/verify-email` | Public; throttled | Activate a pending account with email OTP; customer must log in afterwards |
| POST | `/auth/verification/resend` | Public; throttled; CAPTCHA when enabled | Generic response while resending OTP only for eligible pending accounts |
| POST | `/auth/password/change` | Bearer, throttled | Verify current password, apply existing password policy, rotate session version, revoke every API token, require fresh login |
| POST | `/auth/email/change/request`, `/auth/email/change/confirm` | Bearer, throttled | Reuse the existing 6-month-cooldown email change flow; both steps require the current password, confirm OTP sent to the new address, re-key known account-owned references transactionally, and require login with the new email |
| GET | `/catalog/products`, `/catalog/products/{id}`, `/catalog/categories` | Public | Catalog and image URLs, without binary image blobs |
| GET | `/regions/provinces`, `/regions/cities`, `/regions/districts`, `/regions/villages` | Public | Existing address lookup tables |
| GET/PATCH | `/me` | Bearer | Read profile and update name/mobile |
| GET/POST/PUT/DELETE | `/addresses` | Bearer | Customer-owned address book and default address |
| GET/POST/PATCH/DELETE | `/cart`, `/cart/items` | Bearer | Existing customer cart JSON with server-side product/stock validation |
| GET/POST/DELETE | `/wishlist`, `/wishlist/items` | Bearer | Existing customer wishlist JSON |
| POST | `/shipping/quotes` | Bearer | Quotes for current saved cart/address via existing ShippingService; checks cart/variant/stock and applies per-customer/IP throttling |
| POST | `/checkout/preview` | Bearer | Read-only server calculation of products, voucher, preorder, points, glass service, validated shipping quote, fee, and Midtrans item total |

The entire API is behind `LUNAREA_ANDROID_API_ENABLED`, which defaults to OFF. With it OFF, a local GET returned HTTP 503 JSON `API_NOT_ENABLED`; no database access or mutation occurred.

The local `.env` has no Android API/checkout flag overrides; source defaults keep both `LUNAREA_ANDROID_API_ENABLED` and `LUNAREA_ANDROID_CHECKOUT_ENABLED` OFF. Do not enable either on production until staging gates below pass.

### Password recovery contract

- `POST /api/v1/auth/password-reset/request`: JSON `{ "identity": "email-or-username", "captcha_token": "..." }`. `captcha_token` is required only when the existing reCAPTCHA setting is enabled. A `202` generic response is returned for known and unknown accounts; the OTP is never included in the API response.
- `POST /api/v1/auth/password-reset/complete`: JSON `{ "identity": "email-or-username", "code": "six digits", "password": "...", "password_confirmation": "..." }`. The existing OTP expiry/attempt limits and password-session version rotation apply. The response does not issue a login token; the customer signs in again. Password validation occurs before account lookup to avoid revealing account existence through validation errors.
- Both endpoints require the API master feature flag, password-reset migration tables, and configured mail delivery for actual OTP email. The API request/completion logic was tested with isolated service doubles; no real email was sent.

### Registration and email verification contract

- `POST /api/v1/auth/register`: JSON `{ "name": "...", "email": "...", "phone": "...", "password": "...", "password_confirmation": "...", "consent": true, "captcha_token": "..." }`. Applies the existing disposable-email and Indonesian mobile-number policies, account/password checks, signup throttling, and CAPTCHA when configured. Creates an inactive customer and profile transactionally, claims active auto-claim vouchers when those legacy tables exist, then sends a six-digit email code with a 10-minute expiry. It never issues API tokens.
- `POST /api/v1/auth/verify-email`: JSON `{ "email": "...", "code": "six digits" }`. Activates only an inactive customer account with an unexpired matching OTP and then requires a separate login.
- `POST /api/v1/auth/verification/resend`: JSON `{ "email": "...", "captcha_token": "..." }`. Returns an enumeration-safe generic `202`; only eligible pending accounts receive a newly rotated code after the resend interval. No real email was sent during local tests.
- Native CAPTCHA remains an integration gate: `RecaptchaVerifier` uses Google Siteverify and checks the returned hostname against `Config\Recaptcha::$allowedHostnames`. No Android-native token flow or provider response has been verified. If CAPTCHA is enabled, the APK's register/resend/password-reset actions must obtain a compatible token or the API correctly rejects them; do not bypass server verification to make the app flow appear functional.
- Registration uses the existing legacy `user`/`pembeli` schema and checks required columns, length limits, and InnoDB transaction support at runtime. The production schema and SMTP delivery have not been independently verified; voucher claims are optional only when both legacy voucher tables are absent.
- `POST /api/v1/auth/password/change`: JSON `{ "current_password": "...", "password": "...", "password_confirmation": "..." }`. Requires an authenticated customer bearer token; the current password is rechecked in a transaction, password policy is shared with password recovery, and the password-session version plus all API tokens are invalidated atomically. The customer must sign in again. No password value is logged or returned.
- `POST /api/v1/auth/email/change/request`: JSON `{ "current_password": "...", "new_email": "..." }`; `POST /api/v1/auth/email/change/confirm`: JSON `{ "current_password": "...", "verification_code": "six digits" }`. These endpoints reuse `CustomerEmailChanges`, including the 6-month cooldown, 1-minute resend wait, 10-minute OTP expiry, five-attempt cap, email notification, and existing-account reference re-keying. Confirmation revokes active API token rows, rotates the password-session version, and requires a fresh login with the new email. The transaction verifies both legacy identity rows, dependent updates, commit success, and rolls back the identity migration on failure. SQLite lifecycle tests cover success, token revocation, failed-update rollback, and invalid-code attempt accounting; production schema/transaction behavior remains unverified.
- `POST /api/v1/orders/{id}/payment-proof`: multipart form field `proof` (JPEG, PNG, or WebP, maximum 5 MB). Owner, manual-transfer type, payment-pending status, no prior proof, and non-expired payment are revalidated in the existing transaction-backed service; retries and cross-account order access are rejected. The order ID is the existing Midtrans/order identifier.

## Auth and push implementation

- Opaque access/refresh tokens are random; only SHA-256 token hashes are persisted.
- Access and refresh token issuance is transactional: a failed pair creation rolls both rows back rather than leaving a partial login session.
- Login attempts are throttled by both client IP and normalized account identity to reduce distributed password guessing. Refresh rotation now verifies transaction begin/commit results and the predecessor-to-successor hash link; a persistence failure cannot return a successful token rotation.
- Access lifetime 15 minutes; refresh lifetime 30 days and single-use rotation.
- Token families are revoked on refresh reuse; token validity also tracks the existing password-session version.
- API token issue/authentication fails closed unless `customer_password_sessions` exists; deploy the existing password-reset/session migration before enabling the API.
- FCM device tokens are encrypted using the application's CI4 encrypter before storage; only a SHA-256 token fingerprint is indexed.
- FCM OAuth now accepts only Google's HTTPS token endpoint (`oauth2.googleapis.com/token`), explicitly verifies TLS and disables redirects for OAuth and message requests, sets connect timeouts, and scopes the cached access token by Firebase project. Credentials remain server-side.
- Payment/order-processing/shipping state changes enqueue deduplicated outbox events. `notifications:dispatch --limit 20` sends them using Firebase Cloud Messaging HTTP v1, retries failures, and removes unregistered tokens.
- Keep the Firebase service-account JSON outside the repository and web root. Configure `FIREBASE_PROJECT_ID` and `FIREBASE_SERVICE_ACCOUNT_PATH`; never put service credentials in the Android app.
- Push can be delivered while the app is backgrounded or closed when Android notification permission is granted, the device has network access, the FCM token is current, and the server dispatcher is running. Force-stop, disabled notifications, battery/network restrictions, and provider delivery are OS/FCM-controlled; do not promise instant delivery.
- Schedule the dispatcher under the app's CLI runtime (for example once per minute with `flock`) only after the migration and Firebase configuration are deployed. No cron was installed here.

## Blocking work before Android checkout

1. The first composition of native order/payment creation now exists at `POST /api/v1/checkout/orders`; it remains gated by `LUNAREA_ANDROID_CHECKOUT_ENABLED=false` by default as well as the master API flag. It validates an `Idempotency-Key`, refuses to charge again for replayed requests, checks for an existing pending order, re-runs the full preview inside a transaction, compares the cart/address/price snapshot, requires transactional MySQL tables and expected legacy columns, reserves stock/points/voucher, consumes the shipping quote, persists the legacy-compatible order and shipment, and calls Midtrans only after commit. It retains the cart until Midtrans returns an actionable pending/settlement response; then order status, ledger completion, and conditional cart clearing are committed together. Ambiguous outcomes return HTTP 202 and remain non-rechargeable by that key. The code is not yet proven against production MySQL or Midtrans; do not enable it before staging integration/concurrency tests.

3. Manual bank-transfer proof submission delegates to the existing owner/status/expiry-checked service. Customer cancellation is now exposed at `POST /api/v1/orders/{id}/cancel`; it calls the same payment reconciliation/update path as website cancellation, requires ownership, is rate-limited, checks current Midtrans status before requesting cancel, and verifies provider status again before reporting success. Six focused unit cases cover unpaid eligibility, manual proof review and cancel effects, the pending→cancel→status-confirm sequence, settlement refusal, and invalid-signature refusal (**24 assertions**). This does not substitute for a real Midtrans sandbox test.
4. Validate APIs against a production-schema clone/staging dataset; verify cart variant parsing, address hierarchy columns, shipping quote tables, and existing-order serialization.
5. Validate a real staging BinderByte tracking response with a known staging AWB, then configure a Firebase project and Android application ID and perform a real test-device push end to end.
6. Run production-schema checkout/payment/concurrency tests before enabling Android checkout.
